## 📊 优化前问题诊断

### 1. 草稿与导出记录生命周期混乱
- 草稿221个（79.6%是auto自动保存），导出记录259个
- 代码设计是"导出后删除草稿"，但实际草稿大量累积
- **矛盾**：多房间项目需要多次导出，第一次导出就删除草稿，后续房间无法继续导出

### 2. 记录管理页面展示混乱
- 混合显示草稿和导出记录，用户分不清状态
- **核心问题**：一个项目（如包钢医院33个房间）生成33条导出记录
- 前端没有按项目分组，列表充斥重复项目名称

### 3. 单房间导出 vs 整体报告的矛盾
- **技术实现**：`export_payload`只包含单个`room`，一个房间生成一份报告
- **用户期望**：一个项目生成一份完整报告
- 没有"项目→报告→房间"的层级关系

### 4. 数据追溯性差
- 草稿ID（D开头）、导出ID（X1EXPORT_）、报告编号之间无关联
- 时间戳命名，无业务含义
- 导出记录无法追溯到源草稿

### 5. 性能问题（480个JSON文件）
- 每次打开报告管理页面，遍历221个草稿 + 259个导出记录
- 没有数据库索引，纯文件扫描
- 文件持续增长，性能会越来越差

---

## ✅ 已实施优化（短期+中期）

### 短期优化（不改架构）

#### 1. 报告列表按项目分组折叠 ✅
**文件**: `static/admin.js` - `renderRecords()`函数  
**实现**:
- 按`项目名称+报告编号`分组
- 多条记录的项目显示可折叠分组标题
- 分组内只显示受检区域，避免重复信息

**效果**: 包钢医院33条记录折叠为1个分组，列表清爽易读

#### 2. auto草稿严格7天过滤 ✅
**文件**: `routes/records.py` - `admin_api_records()`函数  
**实现**:
```python
auto_draft_cutoff = time.time() - 7 * 24 * 3600
if draft_kind == 'auto':
    file_mtime = draft_file.stat().st_mtime
    if file_mtime < auto_draft_cutoff:
        continue  # 跳过超过7天的auto草稿
```

**效果**: 从221个草稿减少到45个有效草稿（176个旧auto草稿被隐藏）

#### 3. 受检区域字段显示 ✅
**文件**: `routes/records.py` + `static/admin.js`  
**实现**: 后端API添加`inspection_area`字段，前端列表显示

**效果**: 同项目的多条记录可通过受检区域区分

### 中期优化（局部重构）

#### 1. 创建export_records表 ✅
**文件**: `migrations/002_create_export_records.sql`  
**表结构**:
- 基础字段：export_id, project_id, project_name, report_number, client_name, inspection_area...
- 文件路径：json_path, xlsx_path, docx_path, pdf_path
- 状态字段：template_ready, report_success, overall_status...
- 飞书字段：feishu_report_url, feishu_export_url, feishu_*_status
- 作废标记：voided, voided_at, voided_by, void_reason
- 时间戳：created_at, updated_at

**索引**:
- 单列索引：project_id, project_name, report_number, client_name, operator, detection_date, created_at, voided
- 复合索引：(project_name, report_number) - 用于分组查询

#### 2. 数据迁移 ✅
**文件**: `scripts/migrate_export_records.py`  
**结果**: 成功迁移259条导出记录到数据库

#### 3. API优化：数据库查询 ✅
**文件**: 
- `helpers/records_api_v2.py` - 新版API实现
- `routes/records.py` - 调用v2版本

**架构**:
- **草稿记录**: 仍从文件系统读取（RECORDS_DIR/*.json）
- **导出记录**: 从数据库查询（export_records表）
- 混合结果后统一处理（权限过滤、筛选、分页）

**性能对比**:
| 项目 | 优化前 | 优化后 | 提升 |
|------|--------|--------|------|
| 查询方式 | 遍历480个JSON文件 | SQL查询 + 45个草稿文件 | - |
| 响应时间 | ~300-500ms | **68ms** | **4-7倍** |
| 扩展性 | 线性下降 | 对数增长 | 良好 |

#### 4. 导出时同步数据库 ✅
**文件**: 
- `helpers/export_db_sync.py` - 同步工具函数
- `routes/export.py` - 在导出成功时调用

**实现**: 
- 每次导出成功时自动插入/更新export_records表
- 支持增量更新（飞书上传状态等）

## 🔄 待优化项（长期规划）

### 1. 草稿生命周期管理
**问题**: 多房间项目的草稿删除策略不明确  
**建议**: 
- 设计"项目草稿"和"导出批次"的关系
- 记录每个房间的导出状态，全部导出完成后再删除草稿
- 或者保留草稿，仅标记为"已导出"

### 2. 整体项目报告功能
**问题**: 用户期望一个项目一份报告，但技术实现是一房间一报告  
**建议**:
- 设计"合并报告"功能：将多个房间报告合并为一份完整报告
- 或者提供"项目视图"和"房间视图"两种模式
- 在项目管理系统中建立项目与报告的一对多关系

### 3. 草稿表入库
**问题**: 草稿仍是文件系统存储，无法高效查询  
**建议**:
- 创建`draft_records`表
- 草稿元数据入库，大JSON仍存文件
- 实现草稿列表的数据库查询

### 4. 业务ID关联
**问题**: 草稿ID、导出ID、报告编号、项目ID之间无关联  
**建议**:
- 导出时记录源草稿ID（source_draft_id字段）
- 建立草稿→导出→归档的完整追溯链
- 报告编号与项目ID建立强关联

### 5. 文件存储优化
**问题**: 480+个JSON文件无分类存储，难以管理  
**建议**:
- 按年份/月份分目录存储
- 或者按项目ID分组（需要先解决项目ID问题）
- 定期归档旧文件到冷存储
